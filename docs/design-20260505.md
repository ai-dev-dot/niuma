# Design: Niuma — Compiler-Driven AI Task Orchestration

[English](design-20260505.md) | [中文](design-20260505.zh-CN.md)

## Problem Statement

Systematic waste of idle hardware and compute resources. A 2 GB Ubuntu cloud server sits underutilized.
A cheap weak-model API subscription goes unused. Existing AI agent frameworks (AutoGPT, MetaGPT) assume
resource abundance — 16 GB minimum, unbounded token budgets. Nobody in the literature has attempted
sub-16 GB multi-agent orchestration. **Niuma maps the physical lower bound.**

Core hypothesis: **strong models as compilers, weak models as executors.** The strong model compiles a
natural-language task into a typed DAG with verifiable contracts — once. Weak models fill in typed blanks
inside resource-limited sandboxes, iterating on test failures autonomously. Strong model token cost
drops from O(n) to O(1).

## Constraints

- **Server:** Ubuntu, 2 GB RAM, no GPU. Only the orchestration kernel runs locally.
- **Models:** Both strong and weak models are called via API. No local inference.
- **Token economy:** Strong model tokens are expensive (must conserve). Weak model tokens are cheap (
  burn freely on trial-and-error).
- **Weak model capability:** Called via API (Claude Haiku / Gemini Flash / MiniMax tier). NOT a small
  local model — the model itself is reasonably capable. The bottleneck is the 2 GB deployment
  environment, not model intelligence.
- **Weak model environment:** The worker process runs on 2 GB Ubuntu. Only 1-2 parallel workers.
  Each sandbox subprocess limited to 256 MB RAM, 30s CPU, 64 processes.

## Resource Budget

| Component | Est. Memory |
|---|---|
| OS + base services | ~512 MB |
| Orchestration kernel (Python + SQLite) | ~128 MB |
| Per weak-model subprocess (sandbox) | ~64-128 MB |
| Built-in tools (see Tool Strategy) | ~50 MB disk |
| Headroom | ~256 MB |

**Verdict:** 1-2 parallel workers max on 2 GB. Serial execution is the likely prototype path.

## Application Scope & Verification Strategy

*Added 2026-05-07 — /plan-ceo-review outcome*

The real challenge is not "can the weak model write code" but **"can the weak model's output be
verified in 2 GB?"** Verification is the bottleneck, not generation.

### What CAN be built and verified in 2 GB

| Application type | Verification method | 2 GB feasible |
|---|---|---|
| CLI tools | `subprocess.run()` + stdout/stderr matching | ✅ Lightweight (~16 MB) |
| REST API services | Start server + `curl`/`requests` HTTP validation | ✅ Server process ~32-64 MB |
| Data processing / ETL | Output file comparison, schema validation | ✅ |
| SQLite-backed apps | SQL query result assertion | ✅ |
| SSR HTML output | `html.parser` / `BeautifulSoup` structure check | ✅ |
| Static site generators | File existence + content regex | ✅ |
| npm/pip packages | `pytest` / `jest` unit tests | ✅ |

### What CANNOT be verified in 2 GB

| Application type | Blocker | Why |
|---|---|---|
| Browser-rendered UI | No headless browser fits in 2 GB | Chrome headless ~400 MB, Firefox headless ~300 MB |
| Visual/CSS testing | Needs browser with JS engine | V8/SpiderMonkey alone >100 MB |
| Multi-process services | Memory ceiling | Each extra process subtracts from sandbox budget |
| Desktop GUI | Needs display server | X11/Wayland overhead |
| Mobile apps | Needs emulator | Android emulator >2 GB alone |

### The verification stack

Instead of a browser, niuma verifies web applications through:

```
Layer 1: API contract — curl + jq validate JSON response structure
Layer 2: HTML structure — python html.parser validates SSR output
Layer 3: Database state — sqlite3 queries validate data mutations
Layer 4: File output — file existence + content regex
```

Visual/pixel verification is explicitly out of scope — not possible in 2 GB.

## Tool Strategy

*Added 2026-05-07*

**Approach: Minimal built-in + environment-aware download.**

Niuma ships with a curated base tool set (~50 MB disk). The weak model CAN install additional
packages via pip/npm, but MUST evaluate environment constraints first (available disk, memory,
whether the package exists at the requested version).

### Built-in tools (curated base)

| Category | Tools | Purpose |
|---|---|---|
| Python runtime | `pytest`, `requests`, `flask` | API servers, test execution |
| Node.js runtime | `jest`, `ts-jest`, `typescript` | TypeScript compilation, test execution |
| System tools | `curl`, `jq`, `sqlite3` | API validation, JSON parsing, data queries |
| Code quality | `python -m py_compile`, `npx tsc --noEmit` | Compile-check before sandbox test |

### Download-on-demand (environment-aware)

Before `pip install X` or `npm install Y`, the worker evaluates:

1. **Disk check:** `df -h` — is there enough space?
2. **Memory check:** `/proc/meminfo` — can the sandbox accommodate the package?
3. **Package existence:** Does the package exist? (quick API check)
4. **Install budget:** Is this the right tool for the task, or a random guess?

The worker writes a one-line rationale before installing: "Installing X because [reason]. Disk: Y MB free. Mem: Z MB available." This is logged and reviewable.

### Why not pure built-in

A fixed tool set locks the upper bound of what niuma can build. Users will ask for things that
require libraries outside the built-in set. The environment-aware download approach keeps the
base lean while allowing genuine extensibility.

### Why not pure open

Unrestricted downloading leads to: wrong versions, timeout loops, disk exhaustion, and
non-reproducible runs. The environment check turns "download anything" into "download with
awareness."

## Worker Self-Check Replacement

*Changed 2026-05-07 — /plan-eng-review outcome*

The original `_quick_self_check` asked the weak model "is your code OK? (PASS/FAIL)" — a
self-assessment gate that never failed. Replaced with `_compile_check`: runs the generated
code through `py_compile` (Python) or `tsc --noEmit` (TypeScript) via the existing sandbox.
Zero additional API token cost, zero additional memory.

## Reviewer Structured Output

*Changed 2026-05-07 — /plan-eng-review outcome*

Reviewer output changed from free-text ("PASS" / "FAIL: node — reason") to structured JSON:
`{"verdict": "PASS"}` or `{"verdict": "FAIL", "failed_nodes": [...], "suggestions": "..."}`.
Eliminates fragile regex-based PASS/FAIL parsing. Fallback parser handles legacy text format.

## Architecture

### Data Flow

Git-driven architecture: components exchange data via git and call the next component directly after committing.

```
cli.py creates branch niuma/<task_id>
  │
  │ Conversational requirement clarification (strong model Q&A)
  │ Confirmed → writes .niuma/requirement.md → commit
  │ Calls compiler
  ▼
compiler.py
  reads .niuma/requirement.md
  Strong model generates DAG → commits .niuma/dag.json
  Calls worker(node_1)
  ▼
worker.py
  reads .niuma/dag.json → finds its node
  Weak model generates code → sandbox test → fix → retry
  Passes → commits src/<node_id>.ts
  ├─ Has next node → calls worker(node_next)
  └─ All done → calls reviewer
  ▼
reviewer.py
  reads .niuma/dag.json + src/<node_id>.ts
  Strong model audits → commits .niuma/review.md
  ├─ PASS → done (human reviews git log, decides push)
  └─ FAIL → calls worker (with suggestions, max 3 rounds)
```

### Task State Machine

```
                  ┌──────────┐
                  │ pending  │
                  └────┬─────┘
                       │ cli.py creates branch + clarify
                       ▼
                  ┌───────────┐
            ┌─────│ compiling │─────┐
            │     └─────┬─────┘     │
            │   success  │  failure │ (2× schema validation exhausted)
            │           ▼           │
            │     ┌───────────┐     │
            │     │ executing │     │
            │     └─────┬─────┘     │
            │ all nodes │ node max  │
            │    pass   │ exceeded  │
            │           ▼           ▼
            │     ┌───────────┐  ┌────────┐
            │     │ reviewing │  │ failed │
            │     └──┬───┬────┘  └────────┘
            │  PASS  │   │ FAIL (≤3×)
            │        │   └──→ back to worker
            ▼        ▼
       ┌────────┐  ┌────────┐
       │  done  │  │ failed │ (3× review FAIL)
       └────────┘  └────────┘
```

## DAG Node Specification

Each node in the compiler-generated DAG:

```json
{
  "node_id": "lru_core",
  "name": "LRU Cache Core Data Structure",
  "signature": {
    "language": "typescript",
    "function_name": "LRUCache",
    "params": [{"name": "capacity", "type": "number"}],
    "return_type": "void",
    "allowed_imports": [],
    "methods": [
      {"name": "get", "params": [{"name": "key", "type": "string"}], "return_type": "any"},
      {"name": "put", "params": [{"name": "key", "type": "string"}, {"name": "value", "type": "any"}], "return_type": "void"}
    ]
  },
  "contract": {
    "preconditions": ["capacity > 0"],
    "postconditions": ["get returns the most recently put value, or null"],
    "invariants": ["cache size never exceeds capacity", "least recently used entry is evicted first"]
  },
  "test_skeleton": "test('basic LRU operations', () => { const cache = new LRUCache(2); cache.put('a', 1); cache.put('b', 2); expect(cache.get('a')).toBe(1); cache.put('c', 3); expect(cache.get('b')).toBeNull(); expect(cache.get('c')).toBe(3); });",
  "max_iterations": 10,
  "dependencies": []
}
```

**Fields:**
- `signature` — typed function/method contracts; `allowed_imports` restricts to stdlib
- `contract` — pre/post conditions and invariants in natural language
- `test_skeleton` — auto-executable test code; weak model must satisfy this
- `max_iterations` — weak model retry limit; exceeded → FAILED → back to compiler
- `dependencies` — upstream node IDs for topological ordering

**Compilation validation:** after strong model produces DAG JSON, the kernel validates against
`dag_schema.json` (required fields, type consistency, acyclic dependencies). Up to 2 retries
on schema failure.

## TUI Input Strategy

*Decision recorded 2026-05-07*

牛马 TUI 的所有菜单使用 Python 标准 `input()` 函数（行缓冲模式），不使用 raw terminal 模式（`tty.setraw`/`getch`/转义序列解析）。

**原因：** 目标部署环境（阿里云 2GB 服务器）通过网页终端访问。网页终端（如阿里云控制台的 VNC）在 raw 模式下，方向键的转义序列（`\x1b[A`）经过 TCP/WebSocket 传输后可能被拆分为多个数据包，导致 `[A` 比 `\x1b` 延迟到达。无论设置多大的超时时间，都无法 100% 可靠区分"用户按了 ESC"和"网页终端的上键序列还没传完"。

Python `curses` 能解决此问题但会接管整个终端屏幕，与 `os.system("clear")` 冲突。`input()` 是唯一在所有传输层（SSH、网页终端、本地终端）下 100% 可靠且无需额外依赖的方案。

**具体影响：**
- Tab/ESC/方向键导航 → 改为数字选择 + 回车
- 文本输入、API Key 输入、Token 输入不受影响（本来就是 `input()` 或 `getpass`）

## Prompt Templates (Draft)

### Compiler

System prompt instructs the strong model to decompose a task into DAG nodes with typed signatures,
contracts, and test skeletons. Output is raw JSON with a `"nodes"` array. Per-node constraints:
stdlib imports only, max 5 nodes, all tests must be independently executable.

### Worker

Weak model receives: function signature, contract (pre/post/invariants), completed dependency code
(context injection), and the test skeleton. It outputs only code — no explanation. On test failure,
pytest/Jest output is appended to the prompt: "The code failed. Test output: {output}. Fix it."

### Reviewer

Strong model receives the original task description, full DAG, and per-node generated code + test
output. Scope: contract compliance, signature match, integration correctness. Excluded: style,
performance, docs. Output: `PASS` or `FAIL: <node_id> — <violation> — <suggestion>`.

## Fault Modes

| Fault | Strategy |
|---|---|
| Strong model API timeout | Exponential backoff (1s→2s→4s, max N× configurable), then task failed |
| Weak model API timeout/429 | Exponential backoff (1s→2s→...max 60s), then node FAILED |
| Weak model exceeds max iterations | Node FAILED → back to compiler for re-compilation |
| Subprocess OOM/crash | sandbox captures non-zero exit + stderr; worker uses in fix loop |
| System OOM killer | SQLite persists per-node state; restart recovers in-progress tasks |
| Compiler schema validation failed | Retry strong model with error details (configurable, default 5×) |
| Reviewer FAIL | Retry failed nodes + all downstream dependents (configurable, default 5× rounds) |
| Compile check failed (worker) | Skip test, retry code generation — zero API token cost |
| Multiple nodes fail early | Abort remaining nodes when fail ratio ≥ threshold (configurable, default 0.6) |
| Tool install fails | Log reason, report to reviewer, proceed without the tool |

## SQLite Schema

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY, task_description TEXT NOT NULL, dag_json TEXT,
  status TEXT DEFAULT 'pending', strong_tokens_used INTEGER DEFAULT 0,
  weak_tokens_used INTEGER DEFAULT 0,
  created_at TEXT DEFAULT (datetime('now')), updated_at TEXT DEFAULT (datetime('now'))
);
CREATE TABLE node_results (
  id INTEGER PRIMARY KEY AUTOINCREMENT, task_id TEXT REFERENCES tasks(id),
  node_id TEXT NOT NULL, iteration_count INTEGER DEFAULT 0,
  status TEXT DEFAULT 'pending', generated_code TEXT, test_output TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);
```

## Language Strategy

**Kernel:** Python. **Generated code target:** TypeScript (Python also supported). The DAG node's
`signature.language` field selects the runtime. Adding a new language means implementing a new
sandbox handler — compiler and reviewer are language-agnostic.
