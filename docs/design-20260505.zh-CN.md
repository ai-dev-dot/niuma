## Problem Statement

闲置硬件和算力资源的系统性浪费。用户持有一台 2GB Ubuntu 云服务器和一个弱 LLM 的 token 套餐，都处于低利用率状态。同时，现有的 AI Agent 框架（AutoGPT、MetaGPT）均假设资源富足——最低 16GB 内存，Token 消耗非线性膨胀。在 2GB 环境下跑多 Agent 协作，学术界和工业界都没有先例。

核心假设：**强模型做编译器，弱模型做执行器**——强模型把任务一次性编译成带类型约束和可验证契约的 DAG，弱模型在其中填空，自测自修，直到验证通过。强模型 token 消耗从 O(n) 降到 O(1)。

## What Makes This Cool

**"好货从垃圾硬件里跑出来"。** 这不是功能清单的堆砌——是一个 underdog narrative。2GB 服务器上跑着一整套 AI 调度系统，强模型做一次编译、弱模型多实例并行执行、自动测试验证、最终组装成品。终端里看着弱模型写代码、跑测试、修 bug、全绿——这个过程的 GIF 本身就值得一篇博客。

系统在极端资源约束下的设计决策（为什么选 SQLite 而不是 PostgreSQL、为什么自建轻量队列而不引 Kafka、编译器缓存策略）每一项都是可量化的对比数据，这正是技术博客最有价值的部分。

## Constraints

- **服务器：** Ubuntu，2GB 内存，无 GPU。仅运行编排内核——任务队列、通信、文件管理、日志。
- **模型：** 强模型和弱模型都通过 API 调用，本地不部署任何模型。
- **Token 经济：** 强模型 token 昂贵（必须省着用），弱模型 token 便宜（可以反复试错）。
- **弱 AI 能力：** 弱模型不能做需要判断的决策——它只执行、测试、修复，不理解任务意图。

## Resource Budget

基于 2GB 内存的粗略估算：

| 组件 | 预估内存 |
|---|---|
| OS + 基础服务 | ~512 MB |
| 编排内核（Python 进程 + SQLite） | ~128 MB |
| 每个弱模型子进程（subprocess + 生成代码运行时） | ~64-128 MB |
| 预留 | ~256 MB |

**结论：2GB 下可能只能跑 1-2 个并行弱模型子进程。** 串行执行可能是初始阶段唯一可行的路径。这对方案 A（单机串行原型）没有影响，但对方案 B（分布式并行）意味着：如果要在 2GB 上做多 Worker 并行，子进程必须换成更轻量的执行方式（如同一个 Python 进程内的 `exec()` 沙箱执行），或者将 Worker 外移到其他设备上。

### 安全与沙箱

弱模型生成任意代码并通过 subprocess 执行，即使良性模型也可能产出无限循环、内存泄漏或文件系统破坏性操作。应对策略：

- **Phase 1（原型阶段）：** 使用 `resource.setrlimit` 限制子进程 CPU 时间（30s）、内存上限（256MB）和子进程数。生成的代码写入 `tempfile.mkdtemp()` 创建的临时目录，`subprocess.Popen` 设置 `cwd=tmpdir` + `close_fds=True`。执行后 `shutil.rmtree` 清理。**注意：这会阻止大多数意外但非恶意操作——不够阻止安全攻击，原型阶段可接受。**
- **Phase 2+：** 如果扩展到多设备联邦，每个 Worker 节点应在其自身的受限环境中运行（Docker 容器或最小权限用户）。

这不是可选的——没有沙箱的 AI 代码执行是不可接受的。

## API Rate Limiting

弱模型 API（即使便宜）有 rate limit。弱模型循环中必须包含指数退避策略：首次遇到 429 → 等待 1s → 2s → 4s → 8s（最大 60s），超过最大等待时间则将节点标记为 FAILED 并上报给强模型。

## Premises

1. 强模型只做文本推理——编译任务、审查代码、给出修改指示。不接触代码仓库，不执行工具。
2. 弱模型 token 便宜且充裕，可以大量试错。强模型 token 才是稀缺资源。
3. 强/弱模型都通过 API 调用。2GB 服务器运行编排内核，不跑本地推理。
4. 任务必须被编译成弱 AI 可以独立验证的单元——每个节点附带类型签名、合约描述和可自动执行的测试。
5. 弱 AI 的每个节点都自带可自动验证的测试标准。弱 AI 自己跑测试、看失败、修、重跑，直到全绿——不需要强 AI 中途介入。**注意：弱模型被假定为足以胜任 TDD 的模型（如 Claude Haiku、Gemini Flash 级别），能够基于具体的测试失败信息和编译错误做模式匹配级修复（补 import、修正属性名、对齐类型签名），而非深度架构决策。** 原型阶段的第一步就是实验验证所选弱模型在这个循环中是否可收敛。
6. 如果弱模型超过最大迭代次数仍无法通过测试，该节点标记为 FAILED 并返回给强模型重新编译（触发一次额外的强模型调用以重编译失败节点，包含其失败日志和原 DAG——强模型 token 消耗变为 O(1+ε)，这是异常路径）。
7. **DAG 节点间数据流：** 下游节点通过一个累积的键值上下文对象访问上游节点的输出。上下文包含所有已完成依赖节点的 `generated_code` 和 `node_id`，弱模型 prompt 中注入依赖节点的代码以提供上下文。

## DAG Node Specification (Draft)

每个 DAG 节点的核心结构：

```json
{
  "node_id": "lru_core",
  "name": "LRU 缓存核心数据结构",
  "signature": {
    "language": "python",
    "function_name": "LRUCache",
    "params": [{"name": "capacity", "type": "int"}],
    "return_type": "None",
    "allowed_imports": ["typing", "collections"],
    "methods": [
      {"name": "get", "params": [{"name": "key", "type": "str"}], "return_type": "Any"},
      {"name": "put", "params": [{"name": "key", "type": "str"}, {"name": "value", "type": "Any"}], "return_type": "None"}
    ]
  },
  "contract": {
    "preconditions": ["capacity > 0"],
    "postconditions": ["get(key) 返回最近 put 的值，或 None"],
    "invariants": ["缓存大小不超过 capacity", "最近访问的项在淘汰时最后被移除"]
  },
  "test_skeleton": "def test_lru_cache_basic():\n    cache = LRUCache(2)\n    cache.put('a', 1)\n    cache.put('b', 2)\n    assert cache.get('a') == 1\n    cache.put('c', 3)\n    assert cache.get('b') is None\n    assert cache.get('c') == 3",
  "max_iterations": 10,
  "dependencies": []
}
```

**字段说明：**
- `signature`: 类型约束——弱模型必须产出符合此签名的代码。`allowed_imports` 限定可用的 Python 标准库模块，防止弱模型引入重量级依赖
- `contract`: 前置/后置条件和不变式——强模型用自然语言描述行为约束
- `test_skeleton`: 可自动执行的测试代码骨架——弱模型把生成的代码和这个测试一起跑 `subprocess`
- `max_iterations`: 弱模型最大尝试轮数，超限则 FAILED 回传强模型
- `dependencies`: 此节点依赖的前置节点 ID 列表，决定 DAG 拓扑顺序

**编译验证：** 强模型产出 DAG 后，编排内核先做 JSON Schema 校验——检查必填字段、类型一致性、依赖无环。校验失败则带修复指令重调强模型（编译至多重试 2 次）。

## Prompt Templates (Draft)

### 编译器 Prompt 结构

将自然语言任务描述编译为 DAG JSON。核心约束：

```
你是一个任务编译器。将以下任务描述分解为一个或多个带类型约束和可自动验证测试的子任务。

任务描述：{task_description}

输出要求：
- 每个子任务必须包含：函数签名（语言、函数名、参数类型、返回类型、可 import 的模块列表）
- 行为合约：前置条件、后置条件、不变式（用自然语言）
- 可执行的测试骨架：Python 代码，用于验证生成的实现
- 最大迭代次数（默认 10）
- 依赖关系：此子任务依赖的前置子任务 ID 列表

将输出格式化为有效的 JSON，包含一个 "nodes" 数组。每个节点遵循此 schema：
{sub-schema here}

约束：
- 每个节点的 allowed_imports 仅包含 Python 标准库模块
- test_skeleton 必须是可独立执行的 Python 代码，只依赖预期签名中的函数
- 节点间通过 dependencies 字段声明拓扑关系
- 最多 5 个节点
```

### 弱模型 Worker Prompt 结构

对每个 DAG 节点，弱模型收到的 prompt：

```
你是一个代码生成器。实现以下函数签名，使其通过所有测试。

函数签名：{node.signature}
行为合约：
  前置条件：{node.contract.preconditions}
  后置条件：{node.contract.postconditions}
  不变式：{node.contract.invariants}
可用的导入：{node.signature.allowed_imports}

已完成的依赖节点代码：
{completed_dependencies_context}

测试骨架（你的代码必须通过此测试）：
{node.test_skeleton}

只输出 Python 代码。不要输出解释。
```

弱模型执行循环：

1. 弱模型生成代码 → 写入临时文件
2. subprocess 执行 `python -m pytest test_file.py`（测试文件 = 已生成的代码 + test_skeleton）
3. 如果通过 → 节点完成
4. 如果失败 → 将 pytest 输出追加到弱模型 prompt：「以上代码验证失败。测试输出如下：{pytest_output}。请修复代码。」→ 回到步骤 1
5. 超过 max_iterations → 节点 FAILED

### 审核器 Prompt 结构

```
你是一个代码审查器。检查以下代码是否满足了合约规范。

原始任务：{task_description}
DAG 结构：{dag_json}
每个节点的生成代码和测试结果：
{node_results}

审查范围：
- 合约合规性：每个节点的代码是否满足其前置条件、后置条件和不变式
- 签名匹配：生成的函数是否与声明的签名一致
- 集成正确性：节点间的数据流是否连贯

不要审查：代码风格、性能优化、文档、错误处理细节（除非合约要求）

输出：
- PASS：所有节点满足合约
- FAIL：<具体节点 ID> — <合约违规描述> — <修改建议>
```


## Fault Modes & Recovery

| 故障 | 处理策略 |
|---|---|
| 强模型 API 超时 | 指数退避重试（1s→2s→4s，最多 3 次），超限则任务失败并记录 |
| 弱模型 API 超时/429 | 指数退避（1s→2s→4s→8s，最大 60s），超限标记当前节点 FAILED |
| 弱模型 10 轮迭代仍未通过测试 | 节点标记 FAILED，DAG 节点及其失败日志回传强模型重新编译（异常路径，触发 O(1+ε)） |
| 子进程 OOM/崩溃 | sandbox.py 捕获非零退出码，将 stdout/stderr 附加到失败日志，弱模型据此修复或超限 FAILED |
| 系统 OOM killer | SQLite 持久化每个节点的执行状态。重启后检测 `node_results` 表中未完成的任务，从中断点恢复（而非从头开始） |
| 编译器 JSON Schema 校验失败 | 带错误详情和原始 DAG 重调强模型，最多 2 次；2 次后任务失败 |
| 审核器返回 FAIL | 将审核器的具体修改建议和失败节点 ID 传回弱模型重新执行（不重调编译器，不算额外强模型调用）。审核 FAIL 累积 3 次则任务整体失败 |

### SQLite 持久化模型

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  task_description TEXT NOT NULL,
  dag_json TEXT,            -- 编译器产出的 DAG JSON
  status TEXT DEFAULT 'pending',  -- pending | compiling | executing | reviewing | done | failed
  strong_tokens_used INTEGER DEFAULT 0,
  weak_tokens_used INTEGER DEFAULT 0,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE node_results (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT REFERENCES tasks(id),
  node_id TEXT NOT NULL,
  iteration_count INTEGER DEFAULT 0,
  status TEXT DEFAULT 'pending',  -- pending | running | passed | failed
  generated_code TEXT,
  test_output TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);
```

**重启语义：** 启动时查询 `tasks WHERE status IN ('compiling','executing','reviewing')`：
- `executing` 状态：`node_results` 中 `pending`/`running` 的节点重新入队
- `reviewing` 状态：保留已通过的节点结果，仅重新触发审核器调用（不重跑节点）
- `compiling` 状态：从头重试编译（API 调用是幂等的）

## Cross-Model Perspective

独立子代理的冷读提出了以下关键洞察：

1. **"编译器架构"** — 强模型不直接派发自然语言任务，而是做一次性编译：把高层任务编译成确定性的 DAG 执行图，每个节点带类型签名和可验证契约。弱模型变成"函数体填充器"，在强类型约束的格子里填空。执行图可缓存、可复用——同类型任务第二次进来，强模型零消耗。

2. **Underdog narrative** — "好货从垃圾硬件里跑出来"暴露了用户真实的兴奋点：不是 AI，不是分布式，是对"不可能"的浪漫主义。把限制变成故事。

3. **Temporal 可作为 50% 基础** — 提供持久化执行、任务队列、重试策略。但用户的学习目标是理解分布式调度本身——用 Temporal 会跳过调度器的自建过程，与学习目标冲突。应自建轻量调度器。

4. **周末原型建议** — Python + SQLite + subprocess，单机串行，先证明「编译-执行-验证-审核」闭环能出活。

## Approaches Considered

### 方案 A：单机验证原型
**最小可行。** Python + SQLite + subprocess。串行执行：compiler.py → worker.py（弱模型循环：写代码→跑测试→修→全绿）→ reviewer.py → metrics.py。命令行驱动，周末能跑。

- 产出：终端 demo GIF + Token 消耗对比报告
- 技术栈：Python、SQLite、subprocess、强/弱 API 调用
- 风险：后续扩展需重写，但学习价值在踩坑过程

### 方案 B：分布式调度系统
**理想架构。** 消息队列驱动，多 Worker 并行，持久化执行历史，Web Dashboard。在 2GB 约束下的极致压缩设计。

- 技术栈：Python asyncio 或 Go、SQLite、自建轻量消息队列
- 风险：工程量最大，2GB 约束下并行 Worker 数量可能比预期更少

### 方案 C：编译器优先
**最具创新性。** 先把「自然语言 → 类型化 DAG」做到极致。DAG 可序列化、可缓存、可版本化。弱模型侧极简。

- 技术栈：Python + Pydantic + JSON Schema（DAG 格式）
- 风险：没有可运行的 demo 直观，但设计深度最深

## Recommended Approach

**A + C 合并执行，B 做长期方向。**

编译器（C 的核心）作为方案 A 的第一个模块实现。单机原型验证闭环后，逐步拆出分布式组件向 B 演进。关键路径：

```
设计文档 → 编译器规范 → 单机原型 → 博客第一篇 → 分布式演进 → 跨平台联邦
```

原因：
- 方案 A 验证核心命题最快——学习型项目需要早期正反馈
- 编译器架构是博客最核心的"干货"——DAG 格式定义 + Token 效率对比
- 方案 B 的分布式架构应该在踩过坑之后再画——先跑通串行闭环，坑会告诉你分布式架构应该长什么样
- 三段式学习节奏清晰：调度 → 分布式 → 边缘，每段都能出一篇博客

## Open Questions

1. DAG 序列化格式用 JSON Schema 还是自定义 DSL？JSON Schema 生态好但冗长，DSL 表达力强但需要自己写解析器。
2. 弱模型的最大并行实例数由什么决定——API rate limit 还是 2GB 内存？
3. 编译器缓存策略：DAG 模板如何索引和匹配新任务？相似度阈值怎么定？
4. 验证失败的反馈回路：弱模型按照什么格式汇报失败给强模型？强模型生成修正指令的 prompt 模板怎么设计？

## Success Criteria

- [ ] 编译器：给定一个自然语言任务描述，强模型一次性产出包含 ≥1 个子节点的 DAG（演示任务要求 ≥2 个），每个节点带类型签名 + 合约 + 测试骨架，JSON Schema 校验通过
- [ ] 弱模型执行器：对单个 DAG 节点，弱模型在 ≤10 轮迭代内产出通过所有测试的代码。原型第 0 步：先用一个简单节点（如 LRU 缓存）实验验证所选弱模型在修复循环中可收敛
- [ ] 审核器：强模型审核最终产物，给 pass/fail + 合约违规的具体修改建议，消耗 ≤1500 token
- [ ] Metrics：记录每次强/弱模型 API 调用的 input_tokens + output_tokens、每个节点的迭代次数、通过节点数/总节点数
- [ ] 博客第一篇：完整的架构设计 + 编译器规范 + Demo GIF + Token 效率数据

## Critical Failure Modes (from Test Review)

| 故障 | 有测试 | 有错误处理 | 用户可见 | 风险等级 |
|------|--------|-----------|---------|---------|
| 编译器产出非法 JSON 后重试耗尽 | [→需测试] | ✅ 2 次重试后抛错 | ✅ main.py 报告 CompilationError | OK |
| 弱模型 10 轮迭代不收敛 | [→需测试] | ✅ 回传强模型重编译 | ✅ 日志记录 + FAILED 状态 | OK |
| 审核器 FAIL 累积 3 次 | [→需测试] | ✅ 任务标记 failed | ✅ main.py 报告最终状态 | OK |
| 2GB OOM killer 杀进程 | [→需测试] | ✅ SQLite + 重启恢复 | ⚠️ 静默恢复（无主动通知） | **GAP** |
| 子进程无限循环耗尽 CPU | [→需测试] | ✅ setrlimit(CPU=30s) | ✅ SandboxResult(timed_out=True) | OK |

**1 个关键缺口：** OOM killer 恢复是静默的——系统重启后自动从中断点继续，但没有主动通知机制（如日志中标记「上次运行被 OOM 中断」）。原型阶段可接受，但应该在启动时检测并记录。

## Reviewer Concerns

经过两轮独立审查（6/10 → 7/10），以下问题在文档中已缓解但仍需在实现中验证：

1. **弱模型调试能力的实验验证是最关键的未决风险。** 文档的前提 5 将弱模型定义为"足以胜任 TDD 的模型（如 Claude Haiku、Gemini Flash 级别）"。原型第 0 步就是在动手构建系统之前，用一个简单节点验证所选弱模型在「生成 → 测试失败 → 读报错 → 修 → 重跑」循环中能收敛。如果这一步失败，整个架构需要重新评估。

2. **Prompt 模板是草案，需要在实际调用中迭代。** 编译器和审核器的 prompt 结构已定义，但实际效果取决于强模型的响应质量。JSON 格式输出的稳定性、合约描述的精确度、审核器的误判率——这些都要在真实 API 调用中调参。

3. **子进程执行的安全性在原型阶段仅做 best-effort 限制。** `resource.setrlimit` + 临时目录沙箱能阻止大多数意外行为，但不能防御恶意代码。原型阶段可接受，但任何面向多用户的系统都需要容器级隔离。
