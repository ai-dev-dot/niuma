# 牛马用户手册

## 产品思路

牛马是一个**人和 AI 模型协作写代码**的工具。理解它的核心设计只需要三句话：

1. **项目 = Git 仓库** — 你在牛马里创建的每个项目，背后就是一个 git 仓库。所有工作产物都是 git commit。
2. **模型负责干活** — 强模型把需求拆成可执行计划（DAG），弱模型填空写代码、跑测试、修 bug，强模型最后审核。
3. **人负责决策** — 你通过 Git 菜单看模型的提交记录，判断产出质量，决定 push 还是退回。

你不是在"用 AI 写代码"，你是在**管理一个 AI 开发团队**——你的工作是布置任务、审核结果、拍板发布。

---

## 前置条件

- Python 3.10+
- Node.js（弱模型生成 TypeScript 代码需要）
- Git
- 至少配置了一个强模型和一个弱模型的 API（见下方配置）

首次运行 `./niuma`（或 `./niuma.bat`）会自动检查环境。

## 模型配置

配置文件位于 `~/.niuma/config.json`（用户目录下的 `.niuma` 文件夹）：

```json
{
  "strong": {
    "model": "deepseek-v4-pro",
    "api_key": "sk-xxx",
    "base_url": "https://api.deepseek.com/v1"
  },
  "weak": {
    "model": "MiniMax-M2.7",
    "api_key": "sk-xxx",
    "base_url": "https://api.minimaxi.com/v1"
  }
}
```

- **强模型**：负责编译任务和审核结果，需要推理能力强，token 消耗少但贵
- **弱模型**：负责写代码和修 bug，需要便宜且 token 充裕，可以反复试错

## 核心工作流

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  创建项目     │ → │  布置任务     │ → │  运行管道     │ → │  审核 + Push │
│  (git clone)  │    │  (.tsk 文件)  │    │  (自动执行)   │    │  (人做决定)  │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

### 1. 创建项目

启动 TUI：`./niuma`

在主菜单选择 **N → 新建项目**，输入：
- 项目名称（任意命名）
- Git 仓库地址（如 `https://github.com/ai-dev-dot/niuma-test.git`）
- HTTP 代理（不需要则留空）

TUI 会自动 clone 仓库，项目即创建完成。

> **设计原则**：一个项目绑定一个 git 仓库。模型产出的所有代码、DAG、审核报告都以 git commit 的形式落在这个仓库里。

### 2. 创建任务

进入项目菜单，选择 **2 → 新建任务文件**。任务文件是 `.tsk` 后缀的纯文本，用自然语言描述你想实现的功能。

任务描述的质量直接影响产出。一个好的任务描述应该包含：
- 功能目标（"实现一个 LRU 缓存类"）
- 约束条件（"O(1) 时间复杂度"）
- 具体要求（"get(key) 返回缓存值，不存在返回 null"）
- 目标语言

示例（`tasks/lru-cache.tsk`）：
```
实现一个线程安全的 LRU（最近最少使用）缓存类。

要求:
- 构造函数接收 capacity 参数指定最大容量
- get(key) 方法返回缓存值，不存在返回 null
- put(key, value) 方法存入键值对，超出容量时淘汰最久未使用的项
- 所有操作 O(1) 时间复杂度
- 使用 TypeScript 实现
```

### 3. 运行任务

在项目菜单选择 **1 → 运行任务**，选择对应的 `.tsk` 文件。管道自动执行：

```
强模型编译 → 弱模型执行 → 强模型审核
```

每步的进展和 token 消耗都会实时显示。审核结果为 PASS 或 FAIL（最多 3 轮）。

### 4. 审核模型的工作

任务运行完成后，**不要直接信任结果**。进入项目菜单选择 **3 → Git 提交记录**，查看模型产出的所有 commit：

```
19499fb compiler: DAG for task e3fc810e (2 nodes)
0011c0d worker: implement doubly_linked_list (3 iterations)
4e871de worker: implement lru_cache (2 iterations)
004c75c reviewer: FAIL for task e3fc810e
29a3845 reviewer: PASS for task e3fc810e
```

你应该关注：
- **Complier** 把任务拆成了几个子任务？粒度合理吗？
- **Worker** 每个节点用了多少轮迭代？（迭代多的节点可能设计有问题）
- **Reviewer** 打回了多少次？最终 PASS 的原因是什么？

### 5. Push 或丢弃

- 如果对产出满意：**P → Push 当前分支到远程**
- 如果不满意：不 push，直接在项目内删除分支，回到第 2 步重新写任务描述或调整模型配置

> **核心理念**：Git 是人和模型之间的界面。模型负责 commit，人负责 review 和 push。不要盲目信任模型的产出——你是最终决策者。

## 管道（Pipeline）详解

```
用户任务 (.tsk)
      │
      ▼
┌─────────────┐
│  compiler.py │  强模型（一次调用）
│              │  任务描述 → DAG JSON（含类型签名、合约、测试骨架）
└──────┬──────┘
       │ DAG（子任务列表 + 依赖关系）
       ▼
┌─────────────┐
│  worker.py   │  弱模型循环（每个子任务）
│   + sandbox  │  生成代码 → 自检 → 沙箱跑测试 → 看报错 → 修复 → 重试
│              │  超限 10 轮未通过 → 标记 FAILED，回传强模型重新编译
└──────┬──────┘
       │ 全部子任务通过
       ▼
┌─────────────┐
│ reviewer.py  │  强模型审核（最多 3 轮）
│              │  检查合约合规性 → PASS / FAIL
└──────┬──────┘
       │ PASS
       ▼
  outputs/ 目录 + git 分支就绪
```

### 产出物

- `outputs/<task_id>/` — 每个子任务对应的 `.ts` 文件
- `.niuma/logs/<date>_<task_id>.jsonl` — 完整 API 调用日志
- `.niuma/logs/<date>_<task_id>_summary.json` — 任务汇总（token 消耗、迭代次数等）
- git branch `niuma/<task_id>` — 所有管道步骤的 commit 记录

## Git 作为通信协议

牛马中每一方通过 git commit 留下记录：

| 角色 | Author | 产出 |
|------|--------|------|
| 编译器 | Strong Model | `.niuma/dag.json` |
| Worker | Weak Model | `src/<node_id>.ts` |
| 审核器 | Strong Model | `.niuma/review.md` |

你作为用户，不需要看代码细节。看 git log 就能判断这一轮跑得怎么样：
- commit 数量合理（不是几十个修修补补）
- reviewer 最终是 PASS
- 每个 worker commit 标明了几轮迭代（迭代少 = 一次写对，模型和 DAG 设计都靠谱）

## 日志系统

每次运行自动在 `.niuma/logs/` 下归档，一个任务一个 jsonl 文件。每条记录分两种类型：

- `llm_call` — 每次 API 调用：完整 prompt、response、token 消耗、耗时
- `worker_process` — 弱模型代码提取和沙箱执行结果

日志用于诊断模型问题（如 MiniMax 的 `<think>` 块消耗 token、API 超时频率等），不需要用户日常查看。

## 计划中的功能

### 对话式需求澄清

当前用户直接写 `.tsk` 文件，编译质量完全依赖用户写需求的水平。问题是大多数人不知道怎么写"足够详细"的需求。

计划增加：强模型在编译前先反问用户 2-3 个问题（"这个缓存是什么场景？key 是什么类型？需要 TTL 吗？"），一问一答后生成确认过的需求摘要，再开始编译。

好处：用极低成本（1-2 次强模型调用）减少后续弱模型在错误 DAG 上的 token 浪费。

## 常见问题

**Q: 审核 PASS 了但代码有 bug 怎么办？**

审核器看的是合约合规性，不是穷举测试。如果合约本身不够完整，审核器可能漏掉边缘情况。改进方式是写任务描述时尽量覆盖边界条件。

**Q: 弱模型一直不收敛怎么办？**

查看 `.niuma/logs/` 找到对应任务的 jsonl，看弱模型的 prompt 和 response。常见原因：DAG 拆分太粗（子任务过大）、弱模型本身能力不足（换一个）、API 不稳定（超时导致）。

**Q: 能同时跑多个任务吗？**

当前版本串行执行。并行 Worker 在长期规划中，受限于 2GB 内存约束。
